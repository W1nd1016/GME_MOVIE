# 任务 0.5 · 测试电影的三轮反馈到达

**2026-11-29 已获批并通过验收。** 实现分支为 `feat/0.5-warm-arrivals`。

## 目标与实施前状态

为同一批 1127 部测试电影固定三轮反馈。每种方法在同一测点看到相同的交互，0.3 可以据此逐轮更新电影表示。阶段 0 缺少时间戳，各轮表示模拟的先后顺序。[阶段 0 路线图](../../ROADMAP.md) · [已确认的评估协议](../DECISIONS.md)

| 测点 | 本轮开放的样本 | 每部电影本轮 / 累计条数 |
|---|---|---:|
| cold | 仅使用上架信息 | 0 / 0 |
| warm-1 | 测试侧 A 全部 | 20 / 20 |
| warm-2 | 测试侧 B 的第一组 | 10 / 30 |
| warm-3 | 测试侧 B 的第二组 | 10 / 40 |

探索时已核对 0.1 的 `warm_a.npz`、`warm_b.npz` 和 0.4 的 `holdout.json`。两份源数据各有 22,540 条，覆盖清单中的全部测试电影，每部各 20 条。两份文件内部的（用户，电影）键都唯一，文件之间的键交集为空。实施前权限表允许直接以 `warm_update` 读取整份 A 或 B，当时仓库中尚无模型调用这个入口。[数据架构](../ARCHITECTURE.md) · [用途定义](../../src/coldstart/data/schema.py)

## 划分与产物

1. 从 `artifacts/holdouts/0.4/holdout.json` 取得已验收的 `test_movies`。用 `partition` 用途读取测试侧 A、B，逐份核对电影集合、每部 20 条、用户和电影 ID 均非填充值、交互键唯一，再核对 A 与 B 互斥。出现缺失、重复或重叠时报告来源和电影 ID，停止生成。
2. A 全部进入第一轮。对每部电影的 20 个 B 用户，计算 ASCII 字符串 `gme-warm-v1/<movie_id>/<user_id>` 的 SHA-256，两个 ID 均用无前导零的十进制整数表示。按摘要字节升序排列，摘要相同时按用户 ID 升序打破平局。前 10 个用户进入第二轮，其余 10 个进入第三轮。分组函数只接收交互键，算法版本固定，重排源行、翻转正负标签或更换训练种子均得到相同的组成员。
3. 在 `artifacts/arrivals/0.5/` 写出 `warm_1.npz`、`warm_2.npz`、`warm_3.npz` 和一份 `manifest.json`。每个 NPZ 只含该轮新增的完整样本，沿用 0.1 的 `features`（int32，16 列）和 `label`（uint8）格式，按各自源文件的相对行序写出。清单记录算法版本、所用 0.4 清单的 SHA-256，以及每轮的来源、行数和每部电影新增条数。单轮独立成文件，读取第二轮时只需打开第二轮的交互。校验完成后整体发布目录。重跑相同输入可复用产物，遇到冲突保全已有文件。
4. 0.3 用 `MovieLensDataset(arrivals_root, "warm_2", "warm_update")` 这样的现有调用形式取得当轮的 `(features, label)`。cold 无需打开反馈文件，后续三轮按顺序读取，已开放的历史由 0.3 累积。原始 `warm_a/b` 仅供 `partition`，直接用作更新在文件 I/O 前报错。所有方法在四个测点均以 `final_eval / score` 读取原有的同一完整评分集。

## 风险与面试可讲点

- **为什么按交互键划 B？** 文件重排不应改变哪 10 条先到达。固定哈希顺序可以复现每个用户属于哪一轮，也能避免根据正负样本比例挑分组。模拟到达可用于比较相同反馈预算下的方法表现，真实时间顺序需要带时间戳的数据。
- **怎样证明没有借用未来反馈？** 0.5 用三份独立文件约束每轮能读到的样本，用交互键核验更新集与评分集互斥。0.3 还需要用标签扰动测试验证，改变未来反馈后，当前模型的历史和预测都保持一致。仅有样本互斥还不足以排除历史特征泄漏。
