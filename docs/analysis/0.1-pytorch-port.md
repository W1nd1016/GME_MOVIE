# 任务 0.1 在最终冷启动模型中的位置

**0.1 交付了整个项目共用的两部分：把交互读成有明确用途的样本，以及把一条「用户 × 电影」样本算成一个分数的 PyTorch 底座。** 最终项目要解决的难点是，新电影还没有足够交互时，底座里的“电影向量”从哪里来、怎样随反馈更新。0.1 确定了这个向量在评分模型中的位置，也为后续的生成、校准和评估准备了数据。本文对应实现提交 `97f3952`。

## 一、从整个推荐模型找到 0.1

给定一个用户和一部刚上架的电影，目标是估计这次交互得到正反馈的概率。用户和电影相同，预测时已经看到的反馈数量不同，模型就可能给出不同分数。最终设计有以下层级。[项目路线](../../ROADMAP.md)

```text
新物品冷启动 CTR 排序
├── 物品表示：为评分模型准备当前可用的电影向量
│   ├── 上架时：用物品属性生成初始向量；GME 基线还可利用邻居老电影
│   ├── 有反馈后：用已开放的交互适配或校准电影向量
│   └── 语义 ID 扩展：内容编码 → RQ-VAE 量化 → 与相似物品共享的特征槽位
├── 用户–物品评分：用当前电影表示和用户、属性特征预测正反馈
│   └── CTR 底座（0.1 已实现）
│       ├── 共享 embedding 表 → 按槽位汇总并拼接
│       └── MLP → 每条交互一个 logit
└── 训练与评估：决定各模块可以用哪些交互、怎样检验预测
    ├── MovieLens 输入层（0.1 已实现）
    │   ├── TFRecord 转换 → 六份交互文件 + 物品表 + 清单
    │   └── 用途检查与 Dataset → 特征张量、独立标签
    ├── 底座训练入口（0.1 已用合成数据跑通）
    └── 正式实验（后续）→ 物品级留出、元训练、三轮预热、四个测点评分
```

**阶段 0** 先在 MovieLens 上建立各方法共用的评分底座和评估条件。正式预训练时，老电影的交互会同时训练共享表和 MLP。此后比较冷启动方法时，让各方法为同一部新电影提供不同的电影向量，再交给相同底座评分。这样，方法之间的差异才有机会归因于新电影表示的生成或更新。**0.1 已实现的前向接口是 `BaseDNN.forward(features)`，电影向量目前来自 ID 查表；接入生成器输出是后续任务。** [底座实现](../../src/coldstart/models/base_dnn.py)

**阶段 1 和阶段 2** 延续这个分工。阶段 1 计划在底座预训练时加入语义 ID 槽位，使新老物品可共享部分表示；生成器同时为新物品自身的电影 ID 槽位提供初值。阶段 2 再把早期用户反馈用于校准该向量。路线图将带时间戳的 MicroLens 作为主实验数据。那里复用的是评分结构、槽位设计和反馈可见性的原则，MovieLens 的整数 ID 和本次冒烟权重仅对应当前数据和运行。[语义 ID 与流式训练设计](../../ROADMAP.md)

## 二、真实数据怎样到达各个模型模块

第一次读取旧数据时，一条 TFRecord 可能同时携带当前交互、十个邻居的特征和旧 `hist`。转换器按三种粒度处理它们：当前用户与当前电影形成**交互样本**，电影的固定属性和邻居 ID 汇入**物品元数据**，文件来源和行数写入**清单**。旧 `hist` 含由标签推得的用户信息，在转换时丢弃。这样，后续模块可以单独查一部电影，也可以按指定用途读取一批交互。[转换代码](../../scripts/convert_movielens.py)

### 六份交互文件分别给谁用

左列是实际读取的原始文件，中列均已生成在 `artifacts/movielens/`。右列是正式实验中计划连接的模块。每份 NPZ 都有同样的两个字段：`features` 为形状 `[N,16]` 的 int32 特征 ID，`label` 为形状 `[N]` 的 uint8 二值标签。用途随文件而定。[本机转换清单](../../artifacts/movielens/manifest.json)

| 原始 TFRecord | 转换结果与行数 | 最终连接的位置及标签用途 |
|---|---|---|
| `data/big_train_main.tfrecord` | `base_candidate.npz` · 765,669 | **底座预训练候选池**。其 1,058 部老电影也出现在元训练 A/B。0.4 将按电影划分，仅底座组的交互进入正式预训练，标签用于底座损失。 |
| `data_with_hist/train_oneshot_a_w_ngb_hist.tfrecord` | `meta_a.npz` · 21,160 | **生成器元训练的 support**。0.4 留出的伪新电影先由属性生成向量，再用 A 的标签算适配梯度；只用 A 中的正反馈用户构造适配后的校准信息。 |
| `data_with_hist/train_oneshot_b_w_ngb_hist.tfrecord` | `meta_b.npz` · 21,160 | **生成器元训练的 query**。用 A 适配后的表示预测 B，再用 B 的标签计算 query 损失，训练生成器。评分时的电影表示只依赖此前可见信息。 |
| `data_with_hist/test_oneshot_a_hist.tfrecord` | `warm_a.npz` · 22,540 | **测试电影的第一次更新**。1,127 部新电影各开放 20 条交互，更新后在同一最终集测 warm-1。 |
| `data_with_hist/test_oneshot_b_hist.tfrecord` | `warm_b.npz` · 22,540 | **测试电影的第二、三次更新**。0.5 将每部电影的 20 条按固定、与标签无关的规则拆成 10＋10。每次开放后，才可用该批反馈更新。 |
| `data_with_hist/test_test_w_ngb_hist.tfrecord` | `final_eval.npz` · 123,787 | **四个测点的评分集**。同一批交互在每部电影已开放 0、20、30、40 条时分别预测，再用标签计算 AUC、按用户 GAUC 和 logloss。Dataset 仅允许以评分用途打开此文件。 |

两组 A/B 服务于不同对象：`meta_a/b` 教生成器如何适配一部伪新电影；`warm_a/b` 提供测试电影真正轮到该测点时可见的反馈。阶段 0 的加工交互没有时间戳，这里的先后代表批次开放顺序。正式训练、预热和指标计算都在 0.1 之后。[数据协议](../DECISIONS.md)

### 物品表和清单为何单独存

| 本地产物 | 里面是什么 | 谁读取，接到哪里 |
|---|---|---|
| `artifacts/movielens/items.npz` | 2,185 部电影各一行。按 `movie_id` 对齐 `year`、5 个 `title` ID、5 个 `genres` ID 和 10 个 `neighbors` 电影 ID。 | `load_items(root)` 返回按行对齐的数组，后续属性生成器和 GME 可按目标电影取元数据。GME 再用邻居 ID 定位老电影的表示。当前底座从交互样本直接取得年份、标题和类型，冒烟前向无需查物品表。 |
| `artifacts/movielens/manifest.json` | 每种用途对应的源文件和行数。 | `MovieLensDataset` 先检查用途，再按清单中的行数校验样本数组。清单服务于读取和核对，模型前向只接收特征张量。 |

测试电影的邻居 ID 只存在于最终评估集的**源 TFRecord**。转换时取出固定的邻居电影 ID 即可建立物品表，邻居行中的用户字段和源文件自带的 `hist` 都不会随它进入生成器。已核对邻居均为老电影；原始选邻规则及其上架时可用性未经核实。[转换与物品表校验](../../tests/test_movielens.py)

## 三、把一条交互送进底座

以 `warm_a.npz` 的第一条真实记录为例，用户 ID 为 `6909`，电影 ID 为 `195`，标签为 `1`。下表把同一行的 16 个整数还原成 8 个槽位。这里用这条记录说明前向接口，本次冒烟训练使用独立生成的合成样本。[特征定义](../../src/coldstart/data/schema.py)

| 槽位 | 这一行的值 | 在底座中的去向 |
|---|---|---|
| user、movie、gender、age、occupation、year | `6909, 195, 9, 3, 2217, 11087` | 每个 ID 查出一个 10 维向量。第二个槽位给出电影 195 的向量，后续生成和校准模块正是在这个位置影响打分。年份等数值也是编码后的 ID。 |
| title | `4726, 3232, 2235, 3233, 3234` | 五个标题词 ID 分别查表，再对向量逐维求和，得到一个 10 维标题向量。 |
| genres | `10, 0, 0, 0, 0` | 只有类型 ID `10` 贡献向量。四个填充位置在求和前被掩掉，合计仍是一个 10 维向量。 |

一个 batch 有 `B` 条交互时，数据沿下列方向流动。[Dataset](../../src/coldstart/data/movielens.py) · [底座](../../src/coldstart/models/base_dnn.py) · [训练入口](../../scripts/train_base.py)

```text
MovieLensDataset → DataLoader
  ├─ features [B,16]，torch.long
  │    → 共享 embedding 表 [11135,10] 查表 → [B,16,10]
  │    → 屏蔽 ID 0，按 8 个槽位求和并拼接 → [B,80]
  │    → 无偏置 MLP：80 → 256 → 128 → 1，两个隐藏层用 ReLU
  │    → logits [B]，每条交互一个分数
  └─ labels [B]，torch.float32
       与 logits 一起进入 BCEWithLogitsLoss → 反向传播 → Adam 更新共享表和 MLP
```

训练时标签只走损失这条支路。推理时单条 logit 取 sigmoid 即为模型给出的正反馈概率。对电影 195，后续 cold 测点应使用上架时的表示；等 `warm_a` 的 20 条交互开放后，用户 6909 的正反馈才有资格进入这部电影的可见历史。四个测点改变的是评分时可用的电影表示，同一最终评估集提供待评分的用户–电影对。[训练侧与测试侧协议](../DECISIONS.md)

## 四、0.1 的代码、配置、测试和运行产物怎样接起来

| 类别与文件 | 输入 → 输出，以及它在项目中的位置 |
|---|---|
| 转换 · [scripts/convert_movielens.py](../../scripts/convert_movielens.py) | 在旧 TF1 环境按源文件行序解码，校验同一电影的属性和邻居一致，写出六份样本、物品表和清单。仓库里的配套 CSV 用于测试核对。 |
| 数据定义 · [schema.py](../../src/coldstart/data/schema.py) | 定义特征槽位和“数据集用途 × 读取目的”的准入规则。转换器用它定位电影 ID 和属性，Dataset 用它检查读取，底座用它决定如何分槽。 |
| 读取 · [movielens.py](../../src/coldstart/data/movielens.py) | `MovieLensDataset(root, split, purpose)` 读取交互，向 DataLoader 提供特征和标签；`load_items(root)` 单独提供物品数组。两种读取对应“给一次交互打分”和“为一部电影构造表示”。 |
| 模型 · [base_dnn.py](../../src/coldstart/models/base_dnn.py) | 接收 batch 特征，完成共享查表、槽位汇总和 MLP 打分。槽位宽度由 schema 决定，扩槽测试覆盖增加槽位后的输入维度；真正训练语义 ID 还需要内容编码、码本和带新槽位的底座预训练。 |
| 训练入口 · [scripts/train_base.py](../../scripts/train_base.py) | 读配置，在临时目录写 `synthetic_smoke.npz` 和配套清单，经过同一个 Dataset 和底座训练，然后保存、重载并比较 logits。真实数据的 `base_train` 用途留给 0.4 校验物品级划分后开放。 |
| 训练配置 · [configs/base_smoke.yaml](../../configs/base_smoke.yaml) | 指定 32 条合成样本、种子 123、batch size 8、6 步和 Adam 学习率 0.001，控制这一次 CPU 冒烟。 |
| 运行产物 · [config.yaml](../../runs/0.1-smoke/config.yaml)、[weights.pt](../../runs/0.1-smoke/weights.pt)、[metrics.json](../../runs/0.1-smoke/metrics.json) | 都位于 `runs/0.1-smoke/`。依次是执行配置的副本、共享表与 MLP 的参数、代码提交与逐步训练 loss 等验收记录。脚本将权重载入新的 `BaseDNN`，对同一批输入比较输出。 |
| 数据测试 · [test_movielens.py](../../tests/test_movielens.py) | 从原始数据核对转换字段、行序、最终尾批和物品表。修改旧 `hist` 后应得到相同的解码内容，违规读取最终集应在打开文件前失败。 |
| 模型测试 · [test_base_dnn.py](../../tests/test_base_dnn.py) | 用人工权重手算槽位和与 logit，并验证增加槽位后 MLP 的输入维度会随之变化。 |
| 训练测试 · [test_train_base.py](../../tests/test_train_base.py) | 检查入口拒绝不合格数据；同种子复跑，比较真实送入模型的批次、逐步 loss、最终权重和重载输出。 |
| 工程支持 · [pyproject.toml](../../pyproject.toml)、[.gitignore](../../.gitignore) | 前者声明 PyTorch 包、依赖和测试入口，后者使派生数据、本机运行产物和环境留在工作区。这两项都在模型计算之外。 |

### 这次验收支持什么结论

真实数据走通了**源文件 → 六份 NPZ、物品表和清单 → 可按用途读取**。合成数据走通了**配置 → Dataset → 底座 → 损失和更新 → 权重重载**。0.1 验收记录为 22 项测试通过；冒烟首步和末步训练 BCE 分别为 0.694533 和 0.684380，同种子复跑得到一致权重。要回答“这套方法对新电影推荐效果如何”，还需用 0.4 留出后的真实电影训练底座，并在后续的四个测点比较各方法。这里的单种子 loss 只验证了训练链路。[本机冒烟记录](../../runs/0.1-smoke/metrics.json) · [0.1 验收记录](../plans/0.1-pytorch-port.md)
