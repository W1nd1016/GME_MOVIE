**待用户审批。** 候选分支为 `feat/0.1-pytorch-port`。以下文件、命令和验收条件均为提案，尚未实施或运行。2026-11-28 按新版 [AGENTS.md](../../AGENTS.md) 修订：补充依赖与影响面、物品元数据表和 [ARCHITECTURE.md](../ARCHITECTURE.md) 首版。

## 目标与交付

把现有 MovieLens 数据转成按用途存放的 NPZ 和一张物品元数据表，用 PyTorch 的 Dataset 和 DataLoader 读取，在当前 WSL2 Ubuntu 上用固定种子完成一次可重复的 CPU 训练冒烟。模型结构以旧底座为参照。[路线图任务 0.1](../../ROADMAP.md) · [旧底座](../../base_dnn.py)

| 拟新增或更新的文件 | 用途 |
|---|---|
| `scripts/convert_movielens.py` | 在已有 `gme_movie_tf1` 环境中逐条读取 TFRecord，输出样本 NPZ、物品表 `items.npz` 和含源文件、用途、行数的清单 |
| `src/coldstart/data/schema.py` | 特征槽位定义、数据用途枚举及各用途允许的用法，全项目只在此定义一次 |
| `src/coldstart/data/movielens.py`、`src/coldstart/models/base_dnn.py` | 加载具名数组和物品表，按 schema 汇总特征并输出每条交互的 logit |
| `scripts/train_base.py`、`configs/base_smoke.yaml` | 配置数据、随机种子与训练步数，运行冒烟并保存权重和运行记录 |
| `pyproject.toml`、`.gitignore` | 声明新包与测试依赖，忽略派生数据 `artifacts/`、训练输出 `runs/`、本地环境、`__pycache__/` 和 `.DS_Store` |
| `tests/test_movielens.py`、`tests/test_base_dnn.py`、`tests/test_train_base.py` | 验证转换、物品表、前向计算、数据用途和训练复现性 |
| `docs/ARCHITECTURE.md` | 按实际实现修正 0.1 相关条目，状态改为"已实现" |

任务验收后更新 [进度表](../PROGRESS.md)。需要安装的新依赖将在实施前说明。

**本任务定下、后续任务都会依赖的接口**（细节见 [ARCHITECTURE.md](../ARCHITECTURE.md) §3）：

**已识别的对后续任务的影响**（写入 PROGRESS 的遗留问题）：
- 0.4 将 1058 部老电影拆成底座电影和伪新电影后，部分邻居会落在伪新电影里，失去预训练 ID embedding。1127 部测试电影的邻居共涉及 929 部老电影。0.4 的计划需要统计受影响比例，并决定 GME 基线是过滤这些邻居还是保留。
- 邻居行带有用户槽位（来自 `big_train` 的真实交互）。物品表只保留邻居电影 ID，GME-A/G 按电影 ID 从物品表取属性。

## 数据与训练设计

1. 六种用途各转换一份 TFRecord，来源固定如下，避免把同源 CSV 或 `data/test_oneshot_a.tfrecord` 与 `data_with_hist/test_oneshot_a_hist.tfrecord` 重复计入。保留每个源内的行序，批次顺序的含义由任务 0.5 定义。

   | 用途 | 来源 | 行数 |
   |---|---|---:|
   | `base_candidate` | `data/big_train_main.tfrecord` | 765,669 |
   | `meta_a`、`meta_b` | `data_with_hist/train_oneshot_{a,b}_w_ngb_hist.tfrecord` | 21,160 ×2 |
   | `warm_a`、`warm_b` | `data_with_hist/test_oneshot_{a,b}_hist.tfrecord` | 22,540 ×2 |
   | `final_eval` | `data_with_hist/test_test_w_ngb_hist.tfrecord` | 123,787 |

2. 每条样本只保留二值标签和当前样本的 16 个特征 ID，保留 ID 编码及零填充。旧 `hist` 含标签派生信息，从输出中剔除。标签独立存放，底座前向只接收特征。训练入口拒绝 `final_eval`。
3. **物品元数据表**：按电影 ID 汇总物品侧属性（year、title ×5、genres ×5）和 10 个邻居电影 ID，覆盖 1058 部老电影和 1127 部新电影。邻居字段只出现在带 `w_ngb` 的三个源文件里，测试电影的邻居只存在于 `final_eval` 源文件中。转换时把它们抽取到物品表，下游一律从物品表读取，不需要再打开 `final_eval` 样本。这样既保住了"最终评估集只用于评分"的访问限制，又不丢失 GME 基线需要的邻居信息。
4. 对齐旧底座的共享 `11135 × 10` embedding。6 个单值槽位直接查表，标题和类型各自对 5 个位置做掩码求和，拼成 80 维输入，维度由 schema 计算。沿用无偏置的 `80 → 256 → 128 → 1` 网络、隐藏层 ReLU、交叉熵与 Adam。固定 Python、NumPy、PyTorch 与训练抽样的种子，同一 CPU 环境比较结果。
5. 冒烟配置使用按上述格式生成的小型合成交互，走完整的加载、训练和权重重载流程。`base_candidate` 包含元训练物品，训练入口仅接受合成冒烟数据或已做物品级留出的训练数据，实际 MovieLens 底座训练须使用任务 0.4 的划分。

## 拟执行的验收

计划在仓库根目录执行。第一条使用旧环境，其余命令使用已安装本项目和测试依赖的 PyTorch 环境。

```bash
conda run -n gme_movie_tf1 python scripts/convert_movielens.py --output artifacts/movielens
python -m pytest -q tests/test_movielens.py tests/test_base_dnn.py tests/test_train_base.py
python scripts/train_base.py --config configs/base_smoke.yaml --run-dir runs/0.1-smoke
```

| 具体验收 | 通过条件 |
|---|---|
| `test_conversion_preserves_rows_and_fields` | 对照可读 CSV 核对标签与当前特征。六份记录数与设计第 1 点的表一致。最终集的末条及不足一个 batch 的尾批均可读取 |
| `test_item_table_matches_sources` | 每部电影的属性和邻居在各源文件内恒定、跨文件一致；物品表覆盖 2185 部电影；邻居全部是老电影；物品表不含用户槽位 |
| `test_legacy_hist_is_excluded`、`test_train_rejects_ineligible_splits` | 改变输入样例的旧 hist 后，转换得到的建模数组不变。尝试将 `final_eval` 或未做物品留出的 `base_candidate` 传给训练入口会在更新前报错 |
| `test_base_dnn_slot_pooling_and_logits` | 给定人工权重与一条含 padding 的样例，可逐槽核对求和与 logit。输出每条交互一个有限值；输入维度随 schema 变化 |
| `test_seeded_smoke_and_checkpoint_reload` | 同环境同种子运行两次，批次顺序、逐步 loss 与最终权重一致。至少一个权重发生更新，重新载入后同一样例的预测一致 |

冒烟目录须包含本次配置、git commit、种子、权重及记录训练步数和 loss 的 `metrics.json`。这些数值用于确认训练链路可用。

## 风险、后续边界与面试要点

任务 0.2、0.3 分别实现训练侧和测试侧的历史重建。0.4 决定预训练和伪新物品划分。0.5 生成互斥的三轮预热批次。0.6、0.7 运行基线并报告四个测点的 AUC、GAUC 和 logloss。任务 0.1 的验收依据是数据完整性、物品表正确性、模型计算及训练复现性。

面试时可以结合数据行数检查与字段隔离测试，解释只读 CSV 为什么会丢掉整份最终评估集，以及把旧记录的所有字段直接喂给模型怎样重新引入 `hist` 泄漏。物品表的设计也可以讲：它把"物品侧信息"和"带标签的评估样本"分开，冷启动生成器在不接触评估样本的前提下拿到邻居。

## 计划审查记录（2026-11-28）

审查时用纯 Python 全量解析了七份 TFRecord，核对了本计划依赖的数据事实，并与 AGENTS、ROADMAP、PROGRESS、DECISIONS 对照：

| 检查项 | 结果 |
|---|---|
| 六种用途的行数 | 与原计划一致：765,669 / 21,160 ×2 / 22,540 ×2 / 123,787 |
| `big_train_main` 与元训练 A/B 的电影集合 | 完全相同（1058 部），印证原计划"候选数据须经 0.4 留出"的设计 |

| 邻居字段 | 只在三个 `w_ngb` 文件中；每部电影恒定；全部指向老电影；测试电影的邻居行全部来自 `big_train`，用户都不是该电影在最终评估集里的用户 |
| 与原计划的冲突 | 原计划让训练入口拒绝 `final_eval`，但测试电影的邻居只在该文件里，生成器要用邻居就得读它。本次修订用物品表解决 |
| 与 ROADMAP 的衔接 | 阶段 1 要在底座加语义 ID 槽位（ROADMAP 2.1 第 5 点），本次修订要求输入维度由 schema 计算，提前留出扩展点 |
| 与 AGENTS / PROGRESS / DECISIONS | 无冲突 |
